# 安装流程与依赖处理

版本：1.0 · 2026-10-27。以下为拟实现的用户流程与安装器责任，不是当前已发布的安装教程。两条首版方向必须各自走完本文件的流程。入口：[产品方案](2026-10-27_产品方案-跨设备语音-report.md)。

## 1. 安装体验约定

每个平台提供一个主安装入口，内部安装产品自己的界面、后台和运行库。用户不执行终端脚本、不编辑配置、不寻找 PID，不需要先打开 Codex。第三方软件与系统授权无法由产品擅自代替，向导负责说明、带到准确入口、检查结果并允许继续。

先完成 Deskflow 键鼠连接，再启用语音。首次默认一对设备、一个活动声源，声源所在的键鼠控制电脑作为推荐发送端，Windows 目标电脑作为接收端；不在首版做多声源抢占和多目标广播。Windows 安装包具备发送与接收能力，按用户选择安装/准备相应依赖。

语音角色与 Deskflow 的服务端/客户端是两个概念，界面用“声音从这台电脑发出”“文字输入到这台 Windows”解释；高级信息再显示 Deskflow 角色。

## 2. 依赖分发与安装责任

| 组件 | 哪一端需要 | V1 处理方式 | 权限、版本与失败处理 |
|---|---|---|---|
| 修改版 Deskflow GUI/core | 两端 | 主包交付；自有发行标识，保留上游许可 | 检测原版进程/端口冲突；不覆盖原版设置 |
| Voice Service 与启动管理 | 两端 | 随主包交付；后台随实际用户与安装路径注册 | 日常运行在用户桌面会话；退出/停用状态可见 |
| Qt、TLS/音频运行库 | 相应平台 | 构建锁定并随包部署，附许可 | 不要求用户安装 SDK；完整包验证缺库情况 |
| .NET 运行时 | 保留 C# 的 Windows 后台 | 自包含产物随包交付 | 不依赖 Codex 缓存、系统 SDK 或人工找解释器 |
| Python | 原型脚本使用 | 主链路逐步编译/迁移；正式包不要求用户安装 | 设备组件若仍需解释器，必须独立锁定、许可并随模块部署 |
| 普通系统麦克风 | Mac/Windows 发送端 | 枚举系统已有设备，由用户选择 | 缺少、禁用或权限拒绝时准确提示；不偷换来源 |
| Windows 豆包输入法 | Windows 接收端 | 首选检测已安装版本；缺少时引导官方安装 | 指定支持版本；安装/登录/服务就绪分别检测 |
| VB-CABLE 或已支持虚拟音频设备 | Windows 接收端 | 首版默认官方安装引导；满足分发条件后才纳入引导器 | 驱动安装可能需管理员授权或重启；共享设备不重复安装 |
| SiriRemoteForge/连接组件 | 选择 Siri 的 Mac 发送端 | 作为独立增强模块评估并锁定允许发行的版本 | GPL 兼容边界先审查；保持稳定签名与设备权限 |
| PacketLogger | 当前 Siri 收音方案的 Mac | 用户从 Apple 官方获取，向导验证；不随主包擅自分发 | 来源、版本和授权先核清；缺失则只阻止该声源 |
| Siri HAL 插件与采集后台 | 当前 Siri 收音方案的 Mac | 可选安装步骤，独立清单、授权与卸载 | 安装涉及系统音频/后台；失败必须可回退 |
| Windows Siri 直接收音组件 | 未来 Windows 声源适配 | 本轮不随基础包交付 | 不把普通麦克风 Win → Win 验收算作此设备支持 |

### 第三方获取的固定原则

豆包使用[官方 PC 页面](https://ime.doubao.com/pc)，识别的是输入法，不把豆包聊天客户端当作依赖。若官方当前可下载版本尚未兼容，界面应明确说明；不下载来源不明的旧包或静默关闭用户的输入法更新。

VB-CABLE 官方允许满足条件的分发，需保留来源、可识别性与 donationware 说明；专业分发情形还涉及相应许可。首版默认通过[官方入口](https://vb-audio.com/Cable/)安装，是否随引导器附带由 P-002 根据[官方条款](https://vb-audio.com/Services/licensing.htm)裁定。其他收费或附加 Cable 不能默认按同样条件打包。

Siri 方案的 PacketLogger 依赖与系统组件可见于[项目收音说明](https://github.com/HOLODATA-COM/SiriRemoteForge#microphone)。若未来改用别的采集后端，应重新完成设备兼容和发行审查，不能直接沿用旧结论。主包不自动安装 Apple 开发工具，也不把降低系统保护作为普通安装步骤。

## 3. Mac → Windows 的安装流程

| 步骤 | Mac 发送端 | Windows 接收端 | 继续条件 |
|---|---|---|---|
| A1 安装主包 | 安装有发行签名的 App | 安装主程序和用户态后台 | 两边显示相同产品线、兼容协议版本 |
| A2 接通键鼠 | 设置键鼠控制端与目标屏幕 | 加入该 Deskflow 连接 | 鼠标能够正常跨屏 |
| A3 启用语音 | 选择发送与目标 Windows | 选择接收，确认该发送设备 | 两端明确开启且身份确认完成 |
| A4 准备声源 | 选择普通麦克风；或进入 Siri 增强流程 | 无需在目标机配对源麦克风 | 电平测试有数据，权限与设备状态准确 |
| A5 准备接收 | 显示对端准备状态 | 检测豆包、虚拟音频与版本；必要时引导安装 | 录音输入指向对应虚拟端点，服务兼容 |
| A6 配置按住说话 | 录入不冲突快捷键；Siri 使用设备按键 | 不要求用户手填右 Alt 映射 | 一次按下只产生一个语音会话 |
| A7 测试并保存 | 本地电平与发送状态 | 确认语音条、真实文字和松开停止 | 三层测试分别通过，再标记可使用 |
| A8 登录启动 | 注册本机用户登录启动 | 注册本机交互用户后台 | 两端重启登录后可重新就绪 |

Siri 增强流程依次检查：遥控器已在 Mac 系统配对、必要连接组件签名与版本、PacketLogger、采集后台/HAL、Siri 物理按键事件与专用音频。普通麦克风的测试结果不会使这些检查自动变绿。若用户拒绝系统组件安装，可切换普通麦克风，保持主产品其他能力可用。

Mac 首次权限由系统要求用户确认，页面提供用途与设置入口，重新检测实际状态。权限文案区分麦克风、辅助功能/输入监控和设备组件所需权限，不引导用户一次性开放无关权限。

## 4. Windows → Windows 的安装流程

| 步骤 | Windows A 发送端 | Windows B 接收端 | 继续条件 |
|---|---|---|---|
| B1 安装连接 | 安装主包并完成键鼠控制配置 | 安装主包并加入连接 | 两机键鼠连接正常 |
| B2 选择角色 | 发送声音到 B | 接收来自 A 的语音 | 设备确认完成，方向唯一 |
| B3 准备声音 | 选择 A 的系统麦克风并允许应用访问 | 无需连接 A 的物理麦克风 | A 的本地电平可用 |
| B4 准备文字输入 | 发送本身不要求安装豆包或虚拟驱动 | 检测豆包及接收虚拟音频，完成必要安装 | B 的接收和输入法兼容检查通过 |
| B5 配置触发 | 设置按住说话键，检查本地快捷键冲突 | 通过服务命令启动语音，不依赖共享按键模拟 | A 本地豆包不同时被触发，B 不双重启动 |
| B6 验收保存 | 按住说话、松开 | 在两个普通输入位置实际出字并停止 | 连续会话、切换、重启按计划通过 |

采集枚举避免默认选中本产品接收用的虚拟麦克风，防止音频再次回传形成环路。切换角色时先结束已有会话，不能同时打开两个发送会话。关闭蓝牙或没有 Siri 遥控器不会影响普通系统麦克风路径。

## 5. 接收音频设备的处理

当前验证链为向 `CABLE Input` 播放、由豆包读取 `CABLE Output`。产品页面以“跨设备语音接收音频”解释功能，诊断中保留真实端点名。安装后按实际端点身份枚举和选择，不写死当前电脑的 WinMM 索引、GUID 或设备顺序。

优先设置豆包应用自己的录音设备，并记录变更前状态。不为方便而静默修改整台电脑的默认麦克风；若确需此类变更，必须让用户知道影响并能恢复。输入法设置没有可用受支持接口时，提供准确界面引导与确认，不直接盲写未知版本配置。

## 6. 登录启动、依赖重试与双端启动次序

Mac 由产品用户级 LaunchAgent 管理，Windows 使用普通用户交互登录任务/相应生命周期组件。系统录音与前台输入不放进 SYSTEM 非交互会话；驱动已有系统服务按其安装规范管理。

两台电脑可以以任意先后顺序启动。发送端或接收端尚未登录、网络未就绪、豆包尚未启动时显示等待状态，按有界退避重试。单实例检查基于真实进程身份和组件版本，不能仅看保存的 PID。重连后必须收到新的物理按下才开始下一轮。

停用功能、自启与立即停止是不同操作：关闭语音会结束本产品当前会话；关闭登录启动只改变以后自动准备；退出后台前须完成本轮收尾。界面明确显示这三种操作，后台不把用户明确停用当成需要不断重启的故障。

## 7. 更新、修复与卸载

| 情形 | 安装器/产品责任 |
|---|---|
| 驱动需要重启 | 保存安装进度；明确提示需重启；重启登录后继续检查，不提前显示全部完成 |
| 升级正在录音 | 等待或提示先结束会话，再更新后台与适配器，防止半新半旧 |
| 输入法升级 | 重新识别实际版本/签名；未支持版本停止语音适配并提示，保留键鼠 |
| 安装中途失败 | 回退本产品新增项或给出可恢复进度，不删除原有共享设备 |
| 保留用户数据卸载 | 解除本产品后台、自启、服务与规则，保留用户选择的配置备份 |
| 完整移除本产品数据 | 删除本产品身份/配对与设置；说明设备需重新配对 |
| 已有 VB-CABLE/豆包 | 不把既有共享依赖当成本产品私有文件；不自动卸载 |
| Siri 增强模块卸载 | 只移除经安装清单确认归本模块所有的插件/后台，恢复有记录且仍适用的设置 |

当前两台机器存在原型部署。正式安装前先检查旧组件和自启项，提供迁移预览；等待空闲后停用旧管理器，再导入可验证的设置或重新配对，确认不会双重采集/发键。迁移失败可以恢复原链路。本轮文档没有执行迁移。

## 8. 诊断与失败入口

| 显示状态 | 需要区分的事实 | 恢复入口 |
|---|---|---|
| 本机没有声音 | 未选设备、权限拒绝、设备掉线、错误来源 | 重新选来源、系统权限入口、电平测试 |
| 声音未到对端 | 对端未登录、网络未通、未配对、身份改变 | 连接检查、重新确认设备 |
| 有声音但语音未启动 | 豆包未就绪、版本不支持、适配调用失败 | 输入法检测、版本说明、重试准备 |
| 语音条有反应但不出字 | 录音设备错误、输入位置无效、识别未完成 | 接收设备检查与用户指定测试框 |
| 一次可用后失效 | 未释放会话、服务变化、设备重连 | 状态检查和本产品会话收尾，不取消他人会话 |
| 重启后未就绪 | 自启被关闭、依赖延迟、网络变化 | 自启状态、最近启动原因与可读修复步骤 |

导出诊断需用户操作，默认不含音频、识别正文、完整窗口标题或配对密钥。产品语音层默认不落盘，但不能借此宣称第三方输入法识别全程离线；Siri 下层捕获工具的原始诊断保留另做审计。

## 9. 安装完成的定义

主程序安装成功、依赖存在、网络连通、收到音频、输入法返回成功、用户看到真实出字是不同检查层级。只有收音、到达、实际输入和松开停止分别通过，才完成语音使用设置。没有第二台目标机器时允许完成本地准备，但状态显示“等待对端测试”，不显示端到端已通过。

正式发行前，M6 需要补足本方案两条方向的干净安装、整机重启和升级卸载验收；当前原型的成功不能替代这些结果。详细场景见[分阶段开发计划](分阶段开发计划.md)。
