# 分阶段开发计划

版本：1.0 · 2026-10-27。范围来自用户确认：**V1 必须完成 Mac → Windows、Windows → Windows；Windows → Mac 在后续阶段。** 本文件是开发任务与验收计划，未表示这些任务已执行。入口：[产品方案](2026-10-27_产品方案-跨设备语音-report.md)。

## 1. 推进方式与依赖

采用阶段门槛推进。当前没有完成完整源码归档、许可选型和构建核算，因此不把阶段编号当成已经承诺的周数。M0 输出按工作项估算的工时、实际负责人和日历排期；证书、第三方许可与测试硬件等待单独记录。

M0 → M1 → M2 → M3 → M4 → M5 → M6。UI 原型和依赖安装验证可在 M1 后穿插准备，正式发布必须收齐两条方向的端到端结果。Siri 采集/许可问题的未解决状态只阻挡相关增强模块发行，不能被基础音频成功覆盖。

角色职责：产品负责人确认范围与发行身份；跨平台开发负责人负责协议与 Deskflow 集成；Mac/Windows 负责人负责平台实现；发布负责人负责构建签名与安装；测试负责人保管环境矩阵与真人验收记录。同一人可兼任角色，任务开始前须在 GitHub Issue 中指定实际负责人。

## 2. 阶段与退出门槛

| 阶段 | 工作重点与交付物 | 退出条件 |
|---|---|---|
| M0：定发行边界 | 范围、设备与输入法清单、第三方依赖裁定、仓库身份、测试资源、工时核算 | 两方向均列为 V1；GPL 组合、VB-CABLE、PacketLogger 有明确处理路径；有第二台 Windows 测试资源计划 |
| M1：固化可构建工程 | fork 工程、跨机源码归档、统一 Qt/编译器锁定、现有补丁迁移与干净构建 | Windows/Mac 可从提交构建；不依赖旧应用包拼装、个人绝对路径或 Codex 运行目录 |
| M2：产品化公共服务与 Mac → Windows | 会话状态机、Deskflow 事件接入、独立认证连接、输入法接口、Mac 来源、Windows 接收 | Mac 普通麦克风完整输入通过；原 Mac Siri 体验有独立回归；切换、断线和重复收尾正确 |
| M3：新增 Windows → Windows | Windows 声源与按键捕获、发送端、方向互斥、接收能力复用 | 两台 Windows 真实输入通过；源端不误触发本地豆包，接收端不重复启动录音 |
| M4：做完首次使用与修复 | 语音页面、角色选择、设备确认、录键器、安装检查、测试与诊断 | 新用户能按界面完成配置；故障可定位到声音、传输、输入法或输入位置 |
| M5：打包、升级与卸载 | 两平台安装包、签名、依赖清单、登录启动、迁移、更新、卸载与回退 | 安装不要求开发环境；更新失败可恢复；不移除其他软件共享组件或覆盖官方版 |
| M6：干净机器内测与发布 | 两方向安装/输入矩阵、整机重启、恢复、升级卸载、3–5 组内测报告 | 全部 V1 必测项通过；没有未解释的持续录音、误输入、重复进程或源代码缺失；发布包可追溯到源码 |

M2/M3 可产生明确标注范围的内部预览包，不能在 M2 完成时就把完整 V1 标为完成。

## 4. 两条方向共同的发布验收

以下数量是建议的首版验收门槛，不是当前已完成的测试结果。每份记录包含源码提交、安装包哈希、系统/CPU、声源型号、豆包版本、真实步骤和结果。

| 场景 | 每条方向的要求 | 通过标准 |
|---|---|---|
| 干净安装 | 没有旧桥接、开发工具、Codex 的两个端点 | 按向导完成，运行库随产品处理，不手填路径或 PID |
| 连续说话 | 连续 20 轮，包含短句和约 5 秒语音 | 每次能输入、松开停止、下一轮可用，无持续录音 |
| 换输入位置 | 两个不同普通应用，各至少 5 轮，计入 20 轮 | 下一次按下自然跟随当前位置，无应用登记 |
| 按住时换窗口/屏幕 | 各执行 3 次 | 原会话结束，尾音不迁移，新轮次才能开始；核对无意外输入 |
| 断网、对端退出 | 持有期与空闲期各执行 | 录音和按键有界收尾；恢复后需新按下，不重放 |
| 整机重启 | 发送端、接收端分别重启，再同时重启 | 登录后自动就绪，无人工启动、陈旧 PID 或重复组件 |
| 睡眠、锁屏、声源重连 | 两端按各自平台执行 | 不保持录音；恢复后状态准确，可重新使用 |
| 输入法变化 | 服务重启与不兼容版本情形 | 自动重新检测；未知版本不盲调内部接口；键鼠仍可用 |
| 升级与卸载 | 相邻版本升级、一次失败回退 | 设备身份和设置合理保留；注销自启；不移除共享依赖 |
| 多种来源 | 普通麦克风必测，Mac Siri 增强单列 | 普通来源不依赖 Siri 组件；增强来源缺组件明确失败，不偷换声源 |
| 原 Deskflow 功能 | 键鼠、左右修饰键、剪贴板、原版客户端 | 语音关闭或对端无能力时，既有功能正常 |

Windows → Windows 的最终硬件支持结论至少需要一组真实 Windows 发送机与 Windows 接收机。虚拟机可补故障与安装回归，不能替代所有硬件收音与重启结论。

## 5. 性能与稳定性目标

首版基础麦克风来源的热启动目标：按下到接收语音启动、松开到录音停止，各 P95 不超过 1 秒。识别完成和文字提交受输入法/网络影响，单独记录，不与停止录音时间混算。Siri 采集冷启动延迟单列测量，在设备模块就绪前不展示“已可说话”。这些是设计目标，M2/M3 需实测校准并说明硬件和网络条件。

音频队列保持有界，队列拥塞、设备停顿或格式变化不能造成无限缓存或事后重放。沿用当前 250 ms 量级缓冲作为起始基线，具体采集/播放时钟偏差、等待上限与长按上限在 V-001 的 ADR 中固定，并用异常检查验证。声音、网络与识别失败分别记录。

## 6. 问题处理与发布门槛

持续录音、跨窗口意外输入、重复启动、敏感内容进入诊断、无法卸载、许可未明确、某条首版方向未通过，均为发布阻断项。修复只复测受影响场景及相关公共回归，不反复要求用户完成没有新变化的成功测试。

普通外部依赖缺失若有准确引导和恢复方法，可作为向导的正常路径；未知依赖被伪装成“已就绪”则阻断发行。Siri 设备尚不满足正式发行要求时，该模块不能使用正式支持标记。

## 7. GitHub 进度管理

每阶段建立 Milestone，任务表 ID 对应 Issue，PR 关联 Issue 与验收证明。Issue 必须写清触发条件、预期行为、支持平台、依赖、结果文件和实际负责人。状态使用“未开始、开发中、待验收、已验收、受依赖阻挡”；完成开发不等于完成真人验收。

每阶段结束提交一份可独立评审的记录：本阶段提交范围、通过项目、残留问题、安装包/源码位置和下一阶段入口。M6 的 Release Checklist 只有在两方向证据完整时关闭。操作与目录见[GitHub 工程与发布方案](GitHub工程与发布方案.md)。
