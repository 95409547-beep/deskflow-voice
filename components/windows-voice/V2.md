# V2 Windows receiver

Run the self-contained executable in the logged-on user's interactive session:

```powershell
./deskflow-windows-voice.exe --serve-v2 ./private/receiver-v2.json
```

Use `receiver-v2.example.json` as a schema example. Provision the certificate, its SHA256 pin, a 64-hex-character pairing token through the named environment variable, installation file hashes/signer, a unique installed output-device prefix, and a private state directory. The sample deliberately contains no usable installation pins. Do not commit provisioned settings or logs. The server checks its certificate pin, restricts peers to the configured address, and requires TLS 1.2/1.3 plus token authentication. Starting the listener or completing hello performs no native RPC or audio-device activation. The sender must separately verify the pinned server certificate.

## Framing and handshake

Each message is a four-byte unsigned big-endian length followed by UTF-8 JSON, with a maximum JSON body of 65536 bytes. The client authenticates with:

```json
{"type":"hello","protocol":2,"token":"<pairing-token>"}
```

The server returns:

```json
{"type":"hello","protocol":2,"epoch":"<new-uuid>","receiver":"windows","ready":true,"sample_rate":48000,"channels":1,"format":"s16le"}
```

Every subsequent message in either direction carries that connection's epoch. Wrong or old epochs cannot trigger backend actions. Idle clients send `ping` every three seconds; the server returns `pong` with the epoch. Seven seconds without a complete message closes the connection and cleans up its owned capture. TLS/hello has a five-second deadline; writes have a three-second deadline.

## Sessions

| Direction | Type | Other required fields / result |
|---|---|---|
| Client → server | `begin` | New `session` UUID, `sequence` and `generation` as positive decimal strings without leading zeroes. Sequence strictly increases within the epoch. |
| Server → client | `started` | `session`; sent only after Start/Show succeed and a fresh current microphone start is confirmed. |
| Client → server | `audio` | `session`, `pcm` base64 mono 48kHz signed 16-bit little-endian PCM, 2–19200 bytes, even length. |
| Client → server | `end` | `session`. |
| Server → client | `ended` | `session`, `ready`, `reason`, accepted `audio_bytes` and `frames`. |
| Server → client | `error` | `error` code and `ready`. A busy Begin produces `microphone_busy` without a `started` acknowledgement. |

An exact duplicate active Begin replays `started` without another native Start. A different Begin cannot preempt the active session. End and disconnect cleanup stop an owned capture at most once. The latest 64 completed/cancelled sessions retain their `ended` replies and discard old tail audio, including while a newer session is active. Use a new UUID and increasing sequence after a failed/busy Begin, too. Stop sending after `ready:false`; reconnect only after investigating the backend state.

Normal End drains the bounded 250ms stereo output queue, issues Stop, and confirms microphone end before returning `ready:true`. A drain deadline failure still attempts owned Stop but reports `ready:false`. The configured output receives duplicated stereo samples; the server never selects a system default or changes mute/volume. Cancellation resets queued output, stops its owned capture, and proactively sends `ended`. Reasons include `foreground_changed`, `audio_timeout_2s`, `maximum_hold_60s`, microphone ownership/end changes, or a legacy session becoming active. Connection loss also cleans up ownership. A new session can begin on the same connection after successful cleanup.

Each Begin binds the current foreground HWND, owner PID, process creation time and image identity. Foreground changes or identity reuse cancel the session. The installed service and RPC library are discovered and checked against configured root, file hashes, Authenticode signer and immutable process identity. Only the existing FocusIn/SimpleMessage compatibility exports are used. No transcript, sink, read or commit API is called. Every native call has a one-second deadline; an unknown result terminates only this new helper process and prohibits speculative further RPC.

## Coexistence and validation limits

V2 instances share a user-session mutex. Optional `LegacyReceiverStatus` and `LegacyControllerStatus` paths add read-only idle checks against an existing prototype deployment. The old prototype does not acquire the new mutex, so those checks cannot make it an atomic participant. Keep old and V2 voice gestures serialized during integration. V2 rejects observed busy capture and refuses Stop after its confirmed microphone identity changes; it does not supervise, restart or modify the old processes.

`build.ps1` and `build.ps1 -Publish` run the original 82 assertions plus the added V2 checks entirely with managed fixtures. They do not authenticate a live client, invoke the installed IME, open audio, or establish user-visible transcription acceptance. Live validation must separately cover repeated sessions, end-tail delivery, foreground cancellation, network loss, microphone cleanup, and coexistence with the existing route. A listening/authenticated server alone is not evidence of those results.
